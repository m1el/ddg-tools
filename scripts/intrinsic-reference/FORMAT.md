# Reference outputs of the authors' demo of "Navigating Intrinsic Triangulations"

Generated by `scripts/intrinsic-reference.sh` (rebuilds the demo, regenerates everything). The program is the
MIT-licensed demo `navigating-intrinsic-triangulations-demo` (Sharp, Soliman, Crane 2019; geometry-central v1,
commit 76da12c) built with `-DCMAKE_BUILD_TYPE=Release`, run with `--noGUI` (no window, no display needed, exit code 0).
Every claim below was checked against the files by `scripts/intrinsic-reference/verify_format.py` (largest deviations
printed per run; see "Checks").

## Layout

```
data/intrinsic-reference/<input>/input.obj          copy of the input
data/intrinsic-reference/<input>/<op>/              op = flip | refine25 | refine30
    command.txt     the demo command line (run in this directory; input is ../input.obj)
    stdout.txt      the demo's stdout+stderr
    time.txt        wall time of the whole demo process (read mesh, init, operation, write 5 files); the clock is coarse (~0.1 s steps)
    faceInds.dmat faceLengths.dmat vertexPositions.dmat laplace.spmat interpolate.spmat   the demo's outputs
    stats.txt       from scripts/intrinsic-reference/stats.cpp (same library calls, counts through callbacks)
    analysis.json   from scripts/intrinsic-reference/analyze.py (derived from the files above)
data/intrinsic-reference/SUMMARY.md                 the table at the end of this file
```

Inputs: `spot`, `bob`, `blub` (Crane's model repository: `spot_triangulated.obj`, `bob_tri.obj`, `blub_triangulated.obj`),
`bunny camel camelbad camelbadnonuniform camel_noise1 camelshotnoise bump` (optimal-cones data set), and generated by
`scripts/intrinsic-reference/gen_meshes.py`: `icosphere` (1 subdivision, 42 V), `icosphere_jitter` (same, radially and
sideways perturbed with a fixed LCG, not Delaunay), `thin_cylinder` (open tube, r = 0.1, length 10, 4 vertices around,
12 rings, each ring twisted by 0.37 of a step so that there are no cocircular ties; has boundary), `long_torus`
(8 x 3 vertices, R = 4, r = 0.2, twisted by 0.37 of a step; closed), `sheared_grid` (flat 10 x 10 cells, x' = x + 6 y;
has boundary).

Operations (`command.txt` has the exact flags):

| op | demo flags | meaning |
|---|---|---|
| `flip` | `--flipDelaunay` | intrinsic flips to Delaunay (queue of all edges in edge-index order; an edge is flipped if the opposite angles sum to more than pi; after a flip its 4 neighbouring edges are queued) |
| `refine25` | `--refineDelaunay --refineAngle 25` | Delaunay refinement, minimum angle 25 degrees = the demo's default; no circumradius bound; at most 10 x nVertices(input) insertions |
| `refine30` | `--refineDelaunay --refineAngle 30` | same with 30 degrees (the paper's bound) |

All runs also pass `--intrinsicFaces --vertexPositions --laplaceMat --interpolateMat`. Other things the demo offers
and we did not generate: `--refineSizeCircum R` (maximum circumradius, default inf), `--refineMaxInsertions n`
(0 = no cap, negative = |n| x nVertices, default -10), `.ply` input. Quirks: `--outputPrefix` is parsed but never used
(files go to the working directory under fixed names); the README calls the last file `interpolate.mat`, the program
writes `interpolate.spmat`; refinement on a mesh with boundary prints "[polyscope] [ERROR] Support for refining meshes
with boundary is experimental" to stdout and carries on.

## Common conventions

* Text files, ASCII, `\n` line ends, values separated by single spaces, numbers written with `setprecision(16)`
  (`%.16g`-style: up to 16 significant digits, so doubles are reproduced to about 1e-16 relative, not exactly).
  Integers are plain.
* The first line is a comment, `# dense R C` or `# sparse R C` (R rows, C columns).
* Dense files have exactly R lines of C numbers after the comment. **Dense indices are 0-based** (they are
  vertex indices stored as numbers). **Sparse files are 1-based** in rows and columns (Matlab `spconvert`), one
  `row col value` per line; zero entries are not written; the order is column by column (the demo walks a column-major
  Eigen matrix), rows increasing within a column. Sum duplicates if you build your own matrix (none occur).
* **Vertex order**: intrinsic vertex `i` (row `i` of `vertexPositions.dmat`, row/column `i` of the matrices, value in
  `faceInds.dmat`) for `i < nV_in` is input vertex `i` (index in the OBJ file, 0-based, in order of the `v` lines). The
  vertices added by refinement follow, `nV_in .. nV-1`. Their relative order is the internal order of the
  library (creation order, with the vertices that refinement later removed left out); do not rely on it, identify them by
  position or by their row in `interpolate.spmat`. In `flip` runs `nV = nV_in`.
* **Face order** is internal to the library. It is not the order of the input faces, and it is different between
  `flip` and `refine*`. Compare triangulations as sets (see below), never by position.
* Everything about the input: an OBJ `f` with more than 3 corners is triangulated by the reader (the inputs here
  are all triangles). Input vertices are not merged or removed. Only manifold, oriented meshes are accepted.

## faceInds.dmat and faceLengths.dmat

`# dense nF 3` each; `nF` = number of faces of the intrinsic triangulation. Line `f` of both files describes the same
face. In the face, going round it in counter-clockwise order (the orientation of the input), the three
corners are `v0, v1, v2`:

* `faceInds[f] = (v0, v1, v2)`, 0-based vertex indices (see vertex order). The first corner is whichever corner the
  library keeps as the face's first halfedge; the cyclic order is the orientation, the rotation is arbitrary. For
  comparisons, rotate to the smallest index or compare edge multisets.
* `faceLengths[f] = (l0, l1, l2)` with `l_k` = length of the **edge from corner k to corner (k+1) mod 3**, i.e.
  `l0 = |v0 v1|`, `l1 = |v1 v2|`, `l2 = |v2 v0|`. The corner angle at `v_k` is opposite the edge `l_{(k+1) mod 3}`.
* Lengths are intrinsic edge lengths (geodesic distance along the surface of the straight segment on the input
  mesh), in the units of the input, double precision, 16 digits. They satisfy the strict triangle inequality
  (0 violations in all runs). The same edge has the same length in both of its faces (identical bits in the file).
* **There is no edge numbering.** Edge `{i, j}` is identified by the vertex pair only when it is unique. An edge is the
  pair of halfedges `v_k -> v_{k+1}` in two faces. Interior edge: the halfedge `i -> j` appears in one face
  and `j -> i` in another. A boundary edge appears once, as `i -> j` only (the face lies on its left). Because
  the intrinsic triangulation need not be a simplicial complex (see below):
  * a **double edge** (two different edges between `i` and `j`): the directed pair `i -> j` appears twice (and
    `j -> i` twice); the two edges are told apart by their length (a tie is possible but did not occur in the data);
  * a **self-edge** `i -> i`: a face has the same vertex at two corners, e.g. `(a, a, b)`; the edge from `a` to `a` appears
    as halfedge `a -> a` in two faces (each face counts one halfedge `a -> a`), and a face may carry the same vertex three
    times. Match its two halfedges by the length.
  A comparison "edge lengths per edge, compared as sets" should therefore use the multiset of
  `(min(i,j), max(i,j), length rounded)` over all halfedges, each interior edge counted twice, or (better) the multiset
  over faces of the sorted triple of corner vertices with their lengths. For `flip` runs the multiset of *faces*
  (cyclic triples with lengths) is canonical when there are no cocircular ties.
* Number of edges `nE = (3 nF + nBoundaryHalfedges) / 2` (in `analysis.json`); `nV - nE + nF` equals the Euler
  characteristic of the input in all runs (verified).

## vertexPositions.dmat

`# dense nV 3`. Row `i`: 3D position of intrinsic vertex `i` **on the input surface**: for `i < nV_in` the
input vertex position (read from the OBJ, so equal to its digits), for inserted vertices the point of the
input mesh found by tracing (barycentric interpolation of the corners of its input face). Units of the input,
16 digits. This is the position of the vertex, not an embedding of the intrinsic edges (an intrinsic edge is
generally a curve on the input surface, not the straight segment between its end positions).

## interpolate.spmat

`# sparse nV nV`, 1-based. Row `i` expresses intrinsic vertex `i` as a convex combination of **input** vertices
(columns are always `<= nV_in`, i.e. 0-based `< nV_in`): the barycentric coordinates of its location in an input face
(`vertexLocations[v].inSomeFace()`); zero coefficients are not written. Rows sum to 1 (max deviation 4.4e-16). Rows of the
input vertices are the identity (`i i 1`). An inserted vertex inside an input face has 3 entries (a vertex that
refinement placed on an input edge has 2, on a vertex 1). Multiplying with the input positions reproduces
`vertexPositions.dmat` (max deviation 1.8e-15). This is "data on the intrinsic vertices as a combination of
the input vertices", used as `x_intrinsic = W x_input`.

## laplace.spmat

`# sparse nV nV`, 1-based, the **weak cotan Laplacian of the intrinsic triangulation**: `L_ij = -1/2 sum cot(theta)`
over the (one or two) corners opposite each edge `ij` of the intrinsic triangulation, `L_ii = -sum_{j != i} L_ij`. No mass
matrix, no area normalization, scale invariant. It is symmetric, positive semidefinite (positive diagonal, off-diagonal
entries are negative where the weight is positive; after flipping to Delaunay all weights are non-negative within rounding),
the rows sum to zero. This is the project's sign convention too (`CLAUDE.md`). Double edges add their weights into the one entry
`(i, j)`; a self-edge `i -> i` has no effect on the matrix at all (its two cotan terms cancel between the off-diagonal and the diagonal sum). We assembled the matrix independently from
`faceInds`/`faceLengths` and compared: max deviation 6e-14 on all runs but the extreme ones (`camelshotnoise/flip`
1.4e-7 absolute on entries as large as 1e5 from angles of 0.03 degrees; `sheared_grid` 3e-13; `camel*` flips 5e-12): rounding of
the 16-digit file.

## stats.txt, analysis.json

`stats.txt` is `key value` per line from `stats.cpp` (not an output of the demo): `flips` counts all edge flips,
including those done inside refinement and inside the removal of inserted vertices; `face_insertions` = vertices
inserted into a face (circumcenters), `edge_splits` = edges split (the circumcenter lay outside the triangle across a
boundary edge, boundary-edge splitting); the net number of added vertices is `nV - nV_in`, smaller than
`face_insertions + edge_splits` by the vertices that refinement removed again (`camelbad/refine30` 4,
`camelbadnonuniform/refine30` 4, `sheared_grid/refine30` 92; zero elsewhere); `op_seconds` is the operation alone;
`min_angle_deg_gc` is the library's `minAngleDegrees()`.
`analysis.json`: derived from the faces: angle statistics (minimum/maximum corner angle in degrees, 10-degree
histogram), `self_edges`, `faces_with_repeated_vertex`, `double_edge_pairs` (vertex pairs with at least two
edges), `triangle_inequality_violations`, areas (`area_rel_diff` <= 4e-12), `max_angle_sum_deviation_input_vertices`
(angle sum at the input vertices against the input, <= 9e-8), `delaunay_excess_max_rad` (largest opposite-angle-sum
minus pi over unambiguous interior edges: always <= 0 up to 1e-14, i.e. Delaunay).

## What the reference does (read off the source and the data)

* **Flip** (`flipToDelaunay`): all edges in a FIFO queue, in edge-index order; flip if `alpha + beta > pi` (library tolerance);
  re-queue the four edges around. Boundary edges are never flipped. Result in the data: `is_delaunay` is 1 in every run.
  Without cocircular ties the Delaunay triangulation is unique, so edge lengths agree with any correct implementation; ties
  (regular meshes: `icosphere`, `bunny`, `bump` have 0-1 flips) may resolve differently.
* **Refine** (`delaunayRefine(angle, inf, 10 n)`): flip to Delaunay; repeatedly take the face with the largest area from a
  priority queue (faces touching a boundary edge first) that violates the bound and insert its circumcenter. The
  circumcenter is found by tracing a geodesic **from the face's barycenter** towards the circumcenter (not from the obtuse
  vertex as in the paper; it may cross several faces). If the trace runs into a boundary edge (the circumcenter lies
  outside the surface) the **midpoint of that boundary edge** (in the intrinsic metric, `t = 0.5`) is inserted instead.
  There is no separate encroachment test: a circumcenter that stays inside the surface is inserted even next to the
  boundary. After every edge split (only happens at the boundary) the previously inserted vertices within twice the
  Dijkstra distance of the larger new edge are removed again (this is why some runs add fewer vertices than they
  insert: see stats). Beyond the paper's rule the demo skips a face when (a) exactly one of its three corners is a
  "needle" (the angle sum around that vertex, up to the fixed boundary edges, is below 60 degrees), (b) any
  corner of the input face containing the triangle has input angle sum below 60 degrees, (c) the small corner is at a vertex of degree one,
  (d) the small corner lies between two boundary (fixed) edges. These faces stay below the bound and are **not
  reported anywhere**: `min_angle_deg` in `analysis.json` shows them (`camelshotnoise` stays at 0.04 degrees, `sheared_grid`
  at 2.5 degrees). The loop ends when both queues are empty (it re-checks the whole mesh up to 5 times) or the insertion cap is
  hit; the demo does not say which. The cap was not reached in any run. The demo also counts a failed insertion
  (trace error) silently as a skip.
* **Boundary**: `bump`, `thin_cylinder`, `sheared_grid`, `camelshotnoise` have boundary. The demo processes them without
  complaint, apart from the "[polyscope] [ERROR] ... experimental" line on stdout when refining. Boundary edges are never flipped.
  Refinement may split a boundary edge at its midpoint (see above); that happens in `sheared_grid` only (boundary
  halfedges 40 -> 156 for 25 degrees, 219 for 30 degrees; a boundary edge split repeatedly gives weights 0.5, 0.25,
  0.375 ... in `interpolate.spmat`, always on the two end points of an input boundary edge) and in none of the other
  boundary runs, whose boundary halfedge counts do not change. Inserted boundary vertices have angle sum pi, interior ones 2 pi (to 1e-7).
  On `bump`, 25 degrees needs nothing (minimum angle 25.37 already), 30 degrees inserts 13 interior vertices. Boundary corners
  of the input (e.g. the sheared grid's acute corners) keep their small angles.

## Checks (`scripts/intrinsic-reference/verify_format.py`)

For every run: header sizes; first `nV_in` vertex rows equal the input (exact for the OBJ files, 9e-16 for the generated ones
because they were written with 17 digits and read back as 16); `faceInds` use every vertex and are in range; Laplacian equal to our own assembly;
symmetry exact; interpolation rows sum to 1 and reproduce the positions (<= 1.8e-15); the length of a halfedge equals the length of its twin (exact).
